gomada, rewritten from Go to Rust

The same terminal app for TP-Link Omada controllers: the same commands, the same screens, the same files on disk. The language underneath changed, and the interactive view is now drawn with ratatui. This page says how to run it, what changed, and where the two versions differ.

How to run it

You need a stable Rust toolchain (1.85 or newer) from rustup.rs. Nothing else: no C library has to be installed, and TLS and the keychain client are compiled in.

# get the branch
git fetch origin claude/gifted-hypatia-c2v6z5
git switch claude/gifted-hypatia-c2v6z5

# run from the checkout
cargo run                      # opens the interactive view
cargo run -- --help            # or any command
cargo run -- device list

# or build the executable once and use that
cargo build --release          # about a minute the first time
./target/release/gomada
./target/release/gomada host add home --url https://192.168.0.2:8043 --client-id 9f8e7d

# or install it on your PATH
cargo install --path .

With no host set up, gomada opens a short wizard that asks for the controller address, the client ID, and the client secret, exactly as before. If you already used the Go version on this machine, there is nothing to set up: the Rust version reads the same config file, the same keychain entries, and the same encrypted secret file.

Tests and checks

make check     # fmt, clippy, tests
cargo test     # tests only
make golden    # rewrite expected output

Against a real controller

GOMADA_TEST_URL=https://192.168.0.2:8043 \
GOMADA_TEST_CLIENT_ID=... \
GOMADA_TEST_CLIENT_SECRET=... \
cargo test --test live -- --ignored --nocapture

The test in the second box only reads (sites, devices, clients, Wi-Fi networks). Set GOMADA_TEST_TLS_PIN for a controller with a self-signed certificate.

Differences you can notice

These are all the places where the Rust version behaves differently from the Go version, as far as testing and reading the code showed.

WhereGo versionRust version
Wrong usage wordingCobra's messages, e.g. gomada: unknown command "nope" and a hint lineclap's messages, e.g. error: unrecognized subcommand 'nope' with a usage line. Exit code is 2 in both. Usage errors that gomada itself detects (such as --wired with --wireless) are worded as before.
--help layoutCobra's layoutclap's layout. Same commands, flags, and descriptions.
A value that starts with a dashdevice rename X -bad: "unknown shorthand flag""unexpected argument '-b'". Both exit with 2; in both, write -- -bad to pass it.
Network errors wordingdial tcp 127.0.0.1:1: connect: connection refusedConnection Failed: Connect error: Connection refused (os error 111). The words before it, the hint after it, and exit code 4 are the same.
QR codes patternOne of the eight valid mask patternsAnother one. Same content, same size. A test reads the drawn code back with a QR decoder and compares the content.
--verbose log linesGo's slog text formatSame fields (level, msg, method, url, duration, status), slightly different time and duration notation. Still no headers, bodies, or query strings.
completionbash, zsh, fish, powershellThe same four plus elvish. The scripts are generated by clap, so their content differs.
Proxies removedRequests honored HTTPS_PROXY and NO_PROXYRequests always go straight to the controller. Controllers are normally on the local network; if you reach yours through a proxy, this matters.
Old TLSGo's TLS stackrustls: TLS 1.2 and 1.3 with modern cipher suites only. A controller that offers nothing better than old suites would be refused.
Ctrl+C during a commandThe request was canceled and the command returned an errorThe process ends at once. In the interactive view Ctrl+C quits cleanly, as before.
device upgrade giving up"has not reported back after 20m0s""has not reported back after 20 minutes"
Odd answers from a controller more lenientA null where text or a number was expected was accepted for most fields; a status sent as a string failed the whole listEvery field accepts null, and numbers may arrive as strings everywhere.
Damaged secret file stricterscrypt cost parameters were taken from the file as they wereAbsurd parameters are refused before any work is done, so a hostile file cannot make gomada use gigabytes of memory.
Typed secrets in the view stricterThe text of a prompt stayed in memory until the next promptIt is cleared when the prompt closes.
Version without a release buildgomada dev (commit none, built unknown) in both. Release builds get the version from the tag through GOMADA_VERSION instead of Go linker flags.

Shared stateMutexes, checked by the race detector in testsArc and Mutex, checked by the compiler.

The Rust version has fewer tests: the Go tests were ported by behavior, not one for one, and some were merged. The dependency count also got worse. Rust crates are smaller than Go modules, and the pure-Rust Secret Service client and TLS stack bring most of them. Cargo.lock pins every one.

What was checked

  • Unit and integration tests: 166 pass (121 in the library, 31 for the command line, 13 for the client and core, 1 for environment variables). They run against a Rust port of the fake controller and need no network.
  • The Go golden files: all 23 CLI files and 11 of 12 screen files pass unchanged. The twelfth (the QR screen) was regenerated.
  • Side by side: 100 commands run with the original Go executable and the Rust one, each against a fresh copy of the Go fake controller. 95 give identical output, error output, and exit code; the other 5 are the wording and QR differences in the table above.
  • A real terminal: the interactive view was started in a pseudo-terminal and driven through the tabs, a QR code, the key list, and quit; it exited with code 0 and left the alternate screen.
  • TLS: tests start an HTTPS server with a self-signed certificate and check the probe, refusal without a pin, acceptance with the right pin, refusal with a wrong pin, and the full "add host, then the certificate changes" story.
  • No keychain: on this machine, which has none, host add fell back to the encrypted file, and the token went to the runtime directory with owner-only permissions.
  • Lint: cargo fmt --check and cargo clippy --all-targets -- -D warnings are clean.

What was not checked

Read this before relying on the branch. These could not be tried in the environment the rewrite was made in.

  • A real Omada controller. Everything ran against the fake. The Go version had been used against a real one; the Rust client sends the same requests, but that is an argument, not a test. tests/live.rs is there for this.
  • macOS and Windows. The code compiles for Linux here. The keychain code is written so that entries made by the Go version are found (the same target name on Windows, the same wrapping undone on macOS), but neither system was available. CI now runs the tests on both.
  • A Linux desktop keychain. The Secret Service path (GNOME Keyring, KWallet) was not exercised, only its absence.
  • The release workflow. .github/workflows/release.yml was rewritten for Rust (eight targets, including ARMv6 and ARMv7) and has not run yet. Expect to adjust it on its first run.
  • Test coverage is somewhat thinner than in the Go version (166 test functions against 232), although every golden file and every user-visible flow of the Go tests has a counterpart.
  • Things that were dropped: the 80% coverage floor script, the fuzz target for the response decoder (replaced by a small table of hostile inputs), and the vulnerability scan step. cargo llvm-cov, cargo fuzz, and cargo audit are the Rust counterparts if you want them back.
